# Repository Guidelines

## StreamCap 重构规则

- 以 [StreamCap](https://github.com/ihmily/StreamCap) 为主要行为参考，本地参考目录为与本仓库同级的 `StreamCap` 目录。参考目录只读，构建和运行录播宝应独立于该路径。目标是在 Tauri 2 桌面端重新实现全部界面和用户可见功能，网站继续独立维护。
- 每批功能先记录参考版本或快照、页面入口、默认值、操作结果及异常行为。以 `app/ui/views`、`app/core`、`app/lifecycle`、`app/messages` 和实际使用的 StreamGet 平台能力为起点，持续维护覆盖清单；逐项标注待实现、已实现待验证、已验证及有意差异。分批交付，保留后续平台和功能的范围。
- 界面按桌面操作重新设计。React 展示任务和收集操作，Rust 持有任务状态、调度、平台解析、文件写入和进程生命周期。前端通过 Tauri commands 获取快照和提交操作，通过事件接收状态变化；切换页面或隐藏到托盘后，录制应继续。
- 桌面前端采用 React、TypeScript、Vite、shadcn/ui 和 Tailwind CSS。按页面需要引入组件，筛选条件、选中项和表单草稿优先使用 React 本地状态。任务表需要排序、筛选和批量选择时接入 TanStack Table。
- 桌面界面接近原生应用：内容区三个平台统一（原 macOS 风格），窗口外壳和平台行为随平台，三个平台布局和功能一致，规则见 `docs/design/native-ui.md`，布局原型见 `docs/prototypes/native.html`。**控件一律用 shadcn/ui Nova 默认样式，不改 `src/components/ui/`**；新增组件用 `npx shadcn@latest add <name>`，生成后不改样式。页面里不手写交互控件：按钮、链接式按钮、筛选、搜索框、表头排序、面包屑都用 shadcn 组件的默认 variant 和 size（例如状态筛选用 `Tabs` 的 `line`，搜索框用 `InputGroup`，表头排序用 `Button variant="ghost"`，文字链接用 `Button variant="link"` 或 `BreadcrumbLink`，拼接的控件用 `ButtonGroup`，可按下的选项用 `Toggle`，状态徽标用 `Badge` 自带的 variant，危险操作用 `variant="destructive"`），className 只放布局类（宽度、截断、间距、定位），不改颜色、边框、圆角、阴影和焦点样式；只有左侧导航和设置页左侧分组例外，保持手写，键盘焦点与按钮一致。`Select` 用 shadcn 默认的弹出方式（对齐选中项），不传 `position`。组件按 shadcn 官方示例的结构使用，例如 `SelectItem` 必须放在 `SelectGroup` 里（Nova 的内边距在 `SelectGroup` 上，少了它菜单盖不住按钮，按钮边框会从菜单边缘露出来）。原生感只靠组件以外的部分：token（`src/tokens.css` 设置 shadcn 语义变量 `--radius`、`--background`、`--card`、`--popover`、`--border`、`--input`、`--sidebar` 等和字号，三个平台共用一组值）、页面布局和窗口外壳。内容区三个平台相同（2026-11-23 起统一为原 macOS 的样子，减少三套主题的维护量）：圆角 6px，字号 13px（左侧导航 14px、说明 11px、页面标题 15px 粗体），导航项 36px，内容边距 20px，侧栏 216px，每页顶部 52px 工具栏（标题和摘要上下排列，「添加直播间」是工具栏里带文字的 Teal 按钮），设置页是圆角分组表单，配色为中性浅灰和石墨深色。随平台的只有：字体族（Windows Segoe UI Variable 和微软雅黑 UI，macOS SF 和苹方，Linux Adwaita Sans/Cantarell/Noto Sans CJK）、窗口材质（Windows 11 Mica，macOS 侧栏 vibrancy，Windows 10 和 Linux 不透明底色）、标题栏（Windows 和 Linux 保留系统标题栏；macOS 用 Overlay 标题栏，红绿灯落在侧栏顶部，侧栏顶部留出 52px，工具栏是拖拽区）、滚动条和快捷键写法。页面里的 `win:`、`mac:`、`linux:` 变体只用于外壳差异（目前只有 macOS 为红绿灯留出侧栏顶部），不用来做视觉风格，也不用来改控件外观。焦点样式三个平台统一，在 `src/index.css` 里覆盖 `:focus-visible` 时的 `--tw-ring-shadow`：文本框、下拉框和 InputGroup 外框只把边框变成 Teal，按钮、开关、复选框、toggle、badge、Tabs 触发器和面包屑链接只在键盘操作时出现 2px 实色 Teal 细环；选择器只列这些控件，不影响浮层外框和 aria-invalid。这是「不改 ui 组件」规则里唯一允许的样式覆盖。根节点 `data-platform`（`windows`、`macos`、`linux`，首帧前由 Rust 注入或按 UA 写入）选择字体族和平台行为，`data-material`（`mica`、`vibrancy`、`none`，由 Rust 的 `get_window_material` 决定）决定窗口底是否透明；Windows 10 应用 Mica 失败时退化为不透明底色。明暗模式跟随系统，深色用中性石墨色，避免整体偏蓝。主色固定为 Teal（浅色 teal-700、深色 teal-400），不跟随系统强调色；只有主操作用 Teal 实心按钮（直播间页工具栏的「添加直播间」是带文字的 Teal 按钮），其余用次级按钮或无框按钮；任务表的勾选行和当前行都用 `TableRow` 自带的选中样式（`data-state="selected"`），不另加底色；录像库列表是手写的虚拟列表，选中行用淡 Teal 底；左侧导航三个平台统一为原 Windows 的样子（2026-11-24 起）：侧栏与窗口同底、不画分隔线，图标随文字色，当前项淡灰底加左侧 3×16px 的 Teal 竖条（`index.css` 的 `selection-bar` utility，`--selection-bar-width`/`--selection-bar-height`）；设置分组的当前项只用灰色底，不加竖条。焦点环用 Teal 且只在键盘操作时显示。不用红色或琥珀色表示选中或主操作，以免与录制状态混淆。对话框按钮顺序三个平台统一为主按钮在左（Windows 的习惯；组件里按「取消、主操作」书写，`index.css` 统一反转顺序，不改按钮样式）。侧栏不放品牌标识。界面结构：左侧导航（直播间、录像库、动态、设置），底部状态栏常驻显示 FFmpeg、录制数、码率、磁盘余量和下次检测，直播间页顶部是一行带数字的状态筛选按钮，任务表选中后在右侧显示详情。
- 界面不能有网页感：全局屏蔽浏览器右键菜单（输入框除外），任务行和录像条目用应用自己的右键菜单，菜单项与现有操作一致；界面框架文字不可选中，输入框、详情里的路径和链接、日志用 `select-text` 放开；正式构建在 Windows 和 Linux 上屏蔽浏览器快捷键（刷新、打印、查找、查看源代码、缩放、前进后退等，输入框里的 Alt+方向键放行；Windows 另用 WebView2 的 `AreBrowserAcceleratorKeysEnabled` 关闭），macOS 不拦截，免得挡住系统快捷键和图片、链接拖拽；按钮和列表项用箭头光标，只有外部链接用手形；滚动条随平台。应用快捷键（macOS 用 Cmd，其他平台用 Ctrl）：Ctrl/Cmd+N 添加直播间，Ctrl/Cmd+F 聚焦当前页的搜索框（没有时不做事），Delete（macOS 另有 Cmd+Backspace）删除选中项并确认，Esc 关闭对话框或详情，macOS 上 Cmd+, 打开设置；按钮的悬停提示写出快捷键（`withShortcut`）；用快捷键切换页面前先让输入框失焦，设置页的修改不会丢。窗口大小、位置和最大化状态由 `tauri-plugin-window-state` 记住。
- 任务表用 shadcn `Table` 的默认行高、内边距和表头样式，不设固定行高，不给行加状态底色或透明度。状态只在状态列里表现：录制中用带呼吸动画的红色实心点、检测中用蓝色旋转圆环、等待开播用灰色空心圈、重试中用琥珀色、仅通知用 Teal 铃铛、需处理用红色警告图标、已暂停用灰色文字；各状态均显示文字。
- 后端按功能引入 Tokio、reqwest 和 rusqlite，沿用 serde。平台适配器统一输出直播状态、画质和流信息，参考 StreamGet 的平台行为，逐个平台验证。
- FFmpeg 独立于安装包分发。启动时由 Rust 检查应用本地数据目录中的已验证版本，缺失时在后台按系统和架构自动下载。发布时固定版本、下载地址和 SHA-256，优先国内源，备用源须提供相同文件。分发包使用公用 npm 包 `@seankit/ffmpeg`：读取其 `manifest.json` 中当前平台包的地址（npmmirror 为国内源、npmjs 为备用源）和 SHA-256，tarball 内可执行文件位于 `package/bin/`。该包在独立仓库 `ffmpeg-npm`（与本仓库同级）维护。先下载到临时目录，校验通过后原子安装，再按绝对路径启动。已有可用版本时离线复用；下载期间可使用界面，失败时提供重试并保留可用版本。
- 验收以可观察结果为准。录制功能至少验证未开播、开始录制、断流、手动停止和生成文件可播放；持久化功能验证重启恢复。使用本地样本做可重复测试，平台兼容性另做真实直播间验证。依赖随首个使用场景引入。

## Project Structure

LuBoBao (录播宝) is a Tauri 2 desktop app for live-stream recording, with a headless CLI (`lubobao-cli`) and Docker image built on the same core. The 0.1.0 launch scope and acceptance status live in `docs/feature-map.md`.

- The Rust code is a Cargo workspace (root `Cargo.toml` and `Cargo.lock`, build output in the root `target/`). The version lives in `[workspace.package]`; members inherit it.
  - `crates/lubobao-core` (library): `platforms/` (adapters that resolve a room link into live status, qualities and stream URLs), `recorder/` (FFmpeg process lifecycle, MP4 post-processing), `ffmpeg/` (download, verify and install FFmpeg from `@seankit/ffmpeg`), `tasks/` (task model, SQLite storage, activity, settings), `scheduler/` (polling, concurrency, backoff, shutdown) and `library/`. It must not depend on Tauri or any GUI crate. The `e2e` feature adds a test-only adapter for `e2e+http://…` links; release builds never enable it.
  - `crates/lubobao-cli` (binary `lubobao-cli`): the headless CLI. `run` holds the data-dir lock and serves a local control channel (Unix socket `control.sock` with mode 0600, or a named pipe on Windows); other subcommands go through it, or open the database directly when `run` is not running. See `docs/cli.md`.
  - `src-tauri` (desktop app, depends on `lubobao-core`): `ffmpeg.rs`, `tasks.rs`, `scheduler.rs` and `library.rs` re-export the core modules and add the Tauri glue (`tauri_glue.rs`, `commands.rs`); `desktop/` holds the tray, quit confirmation and notifications. Put `tauri::` code, commands and event emission only here. Commands without `async` run on the main thread, so any command that takes the task lock or touches SQLite or the file system is `async` and does the work in `spawn_blocking` (see `tasks/commands.rs`, `library/commands.rs`).
  - Logging: core and desktop write through the `log` facade (`log::warn!` etc., no `eprintln!`). The desktop app installs `tauri-plugin-log` (`lib.rs`), which writes `lubobao.log` to the system log directory (Windows `%LOCALAPPDATA%\com.xiaofany.lubobao\logs`, macOS `~/Library/Logs/com.xiaofany.lubobao`, Linux `~/.local/share/com.xiaofany.lubobao/logs`) and to stderr, and logs panics; the CLI forwards the facade to its own stderr format (`logging::install`).

- `index.html` mounts `#root` and, before the first paint, sets `data-platform` and `data-material` on `<html>` (from `window.__LUBOBAO_SHELL__`, which `desktop/window.rs` injects, or from the user agent in the browser preview). `src/main.tsx` renders `src/App.tsx`, which holds the current page in React local state; there is no router. Pages are kept alive: once opened, a page stays mounted and non-current pages are hidden (`PageSlot` in `src/components/page-activity.tsx`: invisible, absolutely positioned and `inert`), so data, the library folder, activity filters and loaded pages, scroll positions and settings drafts survive switching. Only the current page reacts to shortcuts and app commands (`useAppCommand` checks `usePageActive()`; Ctrl/Cmd+F skips inputs inside `[inert]`). Hidden pages pause periodic work (`useNow`, library usage polling) and refresh when they become current again (`useOnPageActivate`: the library rereads the current folder silently, settings rereads without overwriting drafts); live event subscriptions keep running. Jumps that carry a target (rooms task, activity task filter, settings group) are seq-numbered requests in `src/components/navigation.ts`, so they also apply to a page that is already mounted.
- `src/components/` holds app components such as `app-sidebar.tsx` and `status-bar.tsx`. shadcn/ui components live in `src/components/ui/`; add them with `npx shadcn@latest add <name>` as pages need them (`components.json` uses the Nova style). Keep them as generated: do not edit their classes or add platform variants there; platform differences go into `src/tokens.css` and page layout. Shared helpers such as `cn` live in `src/lib/`; `src/lib/platform.ts` (platform, shortcuts, drag region), `src/lib/native-behavior.ts` (context menu, browser shortcuts, drag) and `src/lib/app-commands.ts` (shortcut commands for pages) hold the native behaviour.
- `src/pages/pages.ts` lists the navigation pages; page components live in `src/pages/`.
- `src/tokens.css` defines the theme variables: one shared set for all three platforms (light, plus a dark block), platform blocks that only set the font family, and material blocks (`data-material="mica"` / `"vibrancy"`) that make the window, sidebar and (for Mica) status bar transparent. `src/index.css` imports Tailwind CSS v4, maps those variables into the Tailwind theme with `@theme inline`, maps `text-sm`/`text-xs` and the radius scale to the tokens, defines the `win:`, `mac:` and `linux:` variants (window-shell differences only, such as the macOS traffic-light space), and holds the global native-behaviour CSS (selection, cursors, scrollbars, dialog button order); light and dark follow `prefers-color-scheme`. Import with the `@/` alias, which points to `src/`.
- Keep the public homepage and its assets in `website/`. This directory is the Nginx document root and can be deployed directly.
- Implement native commands in `src-tauri/src/lib.rs` and register them with `tauri::generate_handler!`. The desktop entry point is `src-tauri/src/main.rs`.
- Configure the window and installer in `src-tauri/tauri.conf.json`. The window defaults to 1280×800 with a 1024×680 minimum. The main window has `create: false`; `src-tauri/src/desktop/window.rs` creates it from that config and adds the platform parts (transparent window and Mica only on Windows 11, build 22000 and later, an ordinary opaque window on Windows 10; Overlay title bar and sidebar vibrancy on macOS; release-only WebView2 accelerator keys off). `tauri-plugin-window-state` saves only size, position and maximized state. Application icons live in `src-tauri/icons/`.
- Security: `tauri.conf.json` sets a CSP for the bundled pages (`script-src 'self'` plus the hash Tauri adds for the inline script in `index.html`; `style-src` keeps `'unsafe-inline'` for Radix's style attributes, and `dangerousDisableAssetCspModification: ["style-src"]` stops Tauri from adding hashes that would cancel it) and `withGlobalTauri` is off. `capabilities/default.json` lists only what the frontend calls (event listen/unlisten, app version, macOS drag region, opener, directory picker); add a permission there when a page starts using a new plugin or `@tauri-apps/api` call. `npm run tauri dev` loads the Vite server directly, so the CSP only applies to built assets: check it with `npm run tauri build -- --debug --no-bundle`.

## Development and Build Commands

Run commands from the repository root. Install Node.js, npm, and stable Rust. On Windows, install WebView2 Runtime and Microsoft C++ Build Tools with the desktop C++ workload and Windows SDK.

- `npm ci` installs the dependencies pinned in `package-lock.json`.
- `npm run dev` starts Vite at `http://127.0.0.1:1420` for browser-based layout work. The dev server binds to IPv4 loopback because `localhost` can resolve to an unreachable `::1`, which leaves `tauri dev` waiting for the frontend.
- `npm run tauri dev` starts Vite and opens the desktop app with native commands available.
- `npm run build` type-checks with `tsc -b` and builds the frontend into `dist/`.
- `cargo check --workspace` checks the Rust side without building the app. `default-members` excludes `src-tauri`, so a plain `cargo build` or `cargo test` at the root only builds `lubobao-core` and `lubobao-cli` (no GTK/WebKit needed); pass `--workspace` or `-p lubobao` for the desktop crate. The workspace excludes `.claude/` so session worktrees keep their own layout.
- `cargo run -p lubobao-cli -- run` starts the CLI in the foreground; use `--data-dir` to keep test data apart. CLI release builds use `--profile release-cli` (currently the same as `release`; both keep the default `panic = "unwind"` so a panicking task does not take down every recording); output goes to `target/<triple>/release-cli/`.
- `npm run tauri build` builds the desktop app and writes installers to `target/release/bundle/`.

## Coding Style

桌面 CSS token 统一维护在 `src/tokens.css`：一组三个平台共用的值（浅色、深色各一块），平台块只改 `--font-ui`，材质块（`data-material` 为 `mica` 或 `vibrancy`）只把窗口底、侧栏（Mica 另有状态栏）改成透明、Mica 的内容层改成半透明。控件颜色和圆角只用 shadcn/ui 语义名称（组件跟着变）；页面布局另有 `--window`、`--content`、`--selection`、`--statusbar`，尺寸用 `--nav-item-h`、`--page-pad`、`--sidebar-width`、`--header-h`、`--dialog-width`、`--settings-width`、`--text-ui`、`--text-nav`、`--text-dense`、`--text-small`、`--text-title`、`--weight-title`；任务状态使用 `--status-recording`、`--status-waiting`、`--status-checking`、`--status-retrying`、`--status-notify`，出错提示的淡红底使用 `--status-recording-soft`。接入 Tailwind 时将主题映射到同一组变量。

Use two spaces in TypeScript, HTML, and CSS. Name React components in PascalCase and other TypeScript identifiers in camelCase; use kebab-case file names, such as `AppSidebar` in `src/components/app-sidebar.tsx`. Strict TypeScript checks include unused locals and parameters. Use four spaces and snake_case function names in Rust.

## Testing

Rust tests live beside the implementation in `#[cfg(test)]` modules, plus offline fixtures and `#[ignore]` live-network tests under `crates/lubobao-core/tests/`. Name each test after the behavior it checks. There is no frontend test runner yet. Before committing, run `npm run build`, then `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace` from the repository root. Set `LUBOBAO_TEST_FFMPEG` to an ffmpeg binary to run the recorder tests; without it they are skipped. Run live tests with `cargo test -p lubobao-core -- --ignored --nocapture` when a change touches a platform adapter. The CLI end-to-end test (`run`, `add`, recording, `stop`, stream end, SIGTERM) needs `LUBOBAO_TEST_FFMPEG` and runs with `cargo test -p lubobao-cli --features e2e --test e2e -- --nocapture`.

To check the shell manually, run `npm run dev` and open `http://127.0.0.1:1420`; add `?platform=windows`, `?platform=macos` or `?platform=linux` to preview each platform (browser preview only; the desktop app always follows the system). The content area looks the same on all three; only the font family, sidebar top space (macOS), scrollbars and shortcut labels differ. Switch between the four pages, open the add dialog and a row's context menu, check the sidebar, content area, and status bar in both light and dark system themes, and confirm that a 1024px-wide window has no horizontal scrollbar. The browser preview cannot show Mica or vibrancy; check those in the desktop app. Development builds (`npm run dev` and `npm run tauri dev`) also have a debug panel (`src/dev/debug-panel.tsx`, marked「仅开发环境」): open it with Ctrl+Shift+D (Cmd+Shift+D on macOS) or the「调试」button at the right end of the status bar. It switches the platform, the window material (only the page background changes; the real window keeps its material), light/dark (desktop window only, through the Tauri window theme; the browser preview cannot change `prefers-color-scheme`, use the system setting or the devtools emulation) and sample data (desktop window only: the UI switches to `mock-api.ts`, while the real scheduler keeps running in Rust and quit, close and tray prompts still go to the real backend; the browser preview always uses sample data). With sample data it can also open the「发现新版本」dialog and show the rooms list empty or failing to load. Overrides live in URL parameters (`?platform=`, `?material=`, `?theme=`, `?mock=1`, `?tasks=empty|fail`), survive reloads and reset on restart; the entry shows「已覆盖 N 项」and「全部恢复默认」clears them. The panel, its entry and the debug-only `core:window:allow-set-theme` capability are not in release builds; after `npm run build`, searching `dist/` for「仅开发环境」finds nothing.

## CI and Releases

- `.github/workflows/test.yml` runs on every push and pull request on Windows, macOS (arm64), and Ubuntu: `npm run build`, `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` and the CLI end-to-end test. It installs FFmpeg from `@seankit/ffmpeg@9.0.1` and sets `LUBOBAO_TEST_FFMPEG`, so the recorder tests run too; `#[ignore]` network tests are skipped. Run the same three cargo commands locally before pushing.
- `.github/workflows/cli.yml` runs on every branch push and pull request: it builds static musl `lubobao-cli` for x64 (`ubuntu-24.04`) and arm64 (`ubuntu-24.04-arm`), checks the release binary has no test adapter, installs FFmpeg with the CLI itself, runs the end-to-end test, packages `lubobao-cli_<version>_linux_<arch>.tar.gz`, then builds the Docker image per architecture and runs the end-to-end test and a `docker stop` check inside it. Images are only pushed when `release.yml` calls it for a `v*` tag, after the build job's version check, and only as `<version>`; `docker-latest.yml` adds `latest` to that image when the Release is published by hand (skipped for pre-releases). The image is based on `gcr.io/distroless/cc-debian12` (the bundled BtbN FFmpeg needs glibc ≥ 2.28); base images are pinned by digest. Pin all actions to commit SHAs.
- `.github/workflows/release.yml` builds installers without code signing: Windows NSIS (x64), separate macOS dmg for arm64 and x64 (ad-hoc signed), and Linux AppImage and deb built on Ubuntu 22.04. It also calls `cli.yml` for the Linux CLI archives and the Docker image (`ghcr.io/seansongx/lubobao`, multi-arch, pushed as `<version>` only for `v*` tags). Only `v*` tag builds run in the GitHub Environment `release` (deployment rule: `v*` tags only), which holds the Secrets `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`; with them and the real `plugins.updater.pubkey` in `tauri.conf.json` it also builds the in-app update artifacts: `-setup.exe.sig`, macOS `.app.tar.gz` + `.sig` and `.AppImage.sig`, each checked against the configured public key by `scripts/verify-updater-signature.mjs`. Manual runs and forks never sign (warning, no update artifacts); a `v*` tag without the key or with the placeholder public key fails. The build job only has `contents: read`. Files are renamed to ASCII (`lubobao_<version>_<os>_<arch>…`, macOS update packages `lubobao_<version>_macos_<arch>.app.tar.gz`), uploaded as Actions artifacts, and the run summary lists each file's size and SHA-256. Manual runs (`workflow_dispatch`) only build; a `v*` tag also writes the GitHub fallback update manifest `latest.json` with `scripts/updater-latest-json.mjs` (Tauri static format: `windows-x86_64`, `darwin-aarch64`, `darwin-x86_64`, `linux-x86_64`, each with the `.sig` content and the Release download URL built from `GITHUB_REPOSITORY`; fails if any package or `.sig` is missing; not listed in `SHA256SUMS.txt`) and creates a draft GitHub Release with every file, `SHA256SUMS.txt`, `latest.json`, the「更新内容」taken from `docs/release-notes/<version>.md` (the part above `<!-- 以上为应用内更新说明 -->` becomes the in-app update notes; a `v*` tag fails at the start of the build when that file is missing or empty) and first-launch notes.
- `.github/workflows/publish-xiaofany.yml` runs when a Release is published (or by hand with a tag; drafts are refused): it downloads the Release files, checks `SHA256SUMS.txt`, builds a manifest with `scripts/xiaofany-manifest.mjs` (platform, arch, format, kind, signature and the GitHub download URL as fallback for every file) and publishes with `scripts/publish-xiaofany.mjs`, then checks the xiaofany.com version API and the Tauri update API. It needs the Secret `RELEASE_TOKEN` and skips with a notice without it. Its second job (no token needed) writes the release notes into the Release's `latest.json` with `updater-latest-json.mjs --set-notes` and re-uploads it. `publish-xiaofany.yml` only downloads `lubobao*` files, and `xiaofany-manifest.mjs` ignores `latest.json`. `node --test scripts/updater-latest-json.test.mjs` checks the manifest script (run in `test.yml`). `scripts/publish-xiaofany.mjs` is a verbatim copy of `scripts/release.mjs` from the xiaofany.com repository (commit noted in its header); re-copy it instead of editing it.
- The desktop app updates itself with `tauri-plugin-updater` from `https://xiaofany.com/api/update/lubobao/tauri/{{target}}/{{arch}}/{{current_version}}`, falling back to `https://github.com/seansongx/lubobao/releases/latest/download/latest.json` (`src-tauri/src/desktop/update.rs`, `src/components/update-dialog.tsx`). `update.rs` tries the endpoints in order with one updater each (the plugin's headers apply to every endpoint): an error, timeout (30 s per endpoint) or bad status moves on to the next, a 204 from xiaofany.com ends the check, so gray rollouts are not bypassed. The download falls back too (`download_with_fallback`): when the package URL from xiaofany.com fails (network error, HTTP error, timeout, interrupted transfer), it reads the later endpoints (GitHub `latest.json`) again and downloads from there only if the version is exactly the same; otherwise it reports the original download failure. A signature failure on either route is never retried elsewhere, and the package is verified against the signature of the route it came from. The progress event carries `fallback: true` and restarts from 0, and the dialog says it switched to the backup route. Downloading happens before recordings are finished (`install_update` only uses the downloaded package), so a failed fallback never leaves recordings stopped. Only xiaofany.com (and loopback hosts in debug builds) get the random `X-Client-Id` stored in the app data directory; `src-tauri/tests/updater_fallback.rs` checks both fallbacks against local fake servers with tauri's mock runtime (a test-only signing key). `releases/latest` only points at the newest published non-prerelease, so pre-releases are never offered through GitHub. Forks must replace both endpoints and `pubkey`. The app requires the signature to match the announced version (`requireSignedVersion`), and finishes recordings like a quit before installing. It checks about 10 seconds after start and then every 24 hours when `auto_check_update` is on (desktop only; the CLI ignores this key). If installing fails after recordings were finished, the only way out is `restart_after_failed_update`. Debug builds accept `LUBOBAO_UPDATER_ENDPOINT` (comma-separated, tried in order) to point at local test servers. Linux deb installs only get a link to the website. The CLI does not update itself.
- `.github/workflows/deploy-site.yml` rsyncs `website/` to the official site (`lubobao.xiaofany.com`) on pushes to main that touch `website/**` or by manual run, with a deploy key restricted on the server to syncing the site directory; it skips with a notice when the `SITE_DEPLOY_*` secrets are missing. Before syncing, `scripts/version-site-assets.mjs` rewrites the checked-out `index.html` so every local `href="./…"`/`src="./…"` that points to an existing file gets `?v=<first 10 hex of its SHA-256>` (nginx caches CSS, JS and images for 1 hour to 1 day, so returning visitors would otherwise get new HTML with old styles); the repository copy keeps plain paths, and `node --test scripts/version-site-assets.test.mjs` runs in `test.yml`. Server setup is kept outside this repository. `.github/workflows/install-scripts.yml` tests `website/install.sh` (macOS) and `website/install-cli.sh` (Linux) against a local fake `/asset` server, and runs shellcheck.
- Release steps (details, one-time setup and rollback in `docs/release.md`): `node scripts/set-version.mjs <x.y.z>` (updates `package.json`, `package-lock.json`, `tauri.conf.json`, the root `Cargo.toml` `[workspace.package]`, and the workspace crates in `Cargo.lock`; `node scripts/check-version.mjs` verifies them), commit, then `git tag v<x.y.z>` and push the tag. The workflow fails if the tag differs from the app version. Write `docs/release-notes/<x.y.z>.md` and commit it with the version bump (the draft release picks it up), review the draft by hand and publish it; publishing uploads to xiaofany.com and tags the Docker image `latest`.
- A local `npm run tauri build` needs the update signing key; without it pass `--config '{"bundle":{"createUpdaterArtifacts":false}}'`.
