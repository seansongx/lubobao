1. 卸载后保留应用数据目录 `%LOCALAPPDATA%\com.xiaofany.lubobao`（含 FFmpeg、数据库，约 165 MB）和注册表键 `HKCU\Software\Song\录播宝`。这是 Tauri NSIS 模板的默认行为，静默卸载无法选择删除。不阻塞发版，留到后续版本处理。

同一次验收发现的另外 3 个问题已在 main `48ffa57`（提交 `d5a3de8`）修复，有单元测试和 CLI 端到端测试覆盖，还没有在新打的安装包上实机复验：

- 分段录制时详情和动态显示文件名模板 `…_%03d.ts`：现在显示第一个分段 `…_000.ts`，「录制结束」写实际写出的文件和分段数。
- 手动「停止录制」没有记成用户操作：「录制结束」现在写明原因（手动停止、暂停监控、应用退出、直播结束或断流、网络错误）。
- 手动停止后没有「重新开始录制」的入口：详情面板新增「重新开始录制」，命令行新增 `lubobao-cli start`。

暂不包含：其他平台、桌面通知以外的通知渠道、定时关机、英文界面、统计与公告、录后脚本、时间字幕、应用内播放器、Web 远程管理、代码签名（Windows SmartScreen 和 macOS Gatekeeper 会提示未签名，需购买证书后加入）。

**状态判定**：任务是否启用监控、直播间是否开播、录制文件是否正在写入应分别记录。例如「已开播＋仅通知」与「已开播＋磁盘不足」都没有写文件，但前者是正常结果，后者需要用户处理。界面重开后以 Rust 返回的快照恢复状态。参考 `recording_status_model.py`、`record_manager.py` 和 `stream_manager.py`。

**默认行为对照**：上游默认每 180 秒轮询、每平台最多 3 个并发请求、输出 TS、每 1800 秒分段、录后转 MP4 并保留原件。后续逐项确定录播宝默认值；有意修改时，在对应功能项记录差异及验收结果。

**有意差异 · FFmpeg 获取**：上游在 Windows 上从蓝奏云分享链接下载压缩包，在 macOS 和 Linux 上调用 `brew`、`yum` 或 `apt` 安装，均不校验文件（`app/scripts/ffmpeg_install.py`）。录播宝改为下载公用 npm 包 `@seankit/ffmpeg` 中当前平台的包（FFmpeg 9.0.2 GPL 构建，只取 `ffmpeg`），按固定 SHA-256 校验后安装。

**有意差异 · 抖音解析**（参考 StreamGet v4.0.10，提交 `e57e548`）：
- 取流请求头只带 User-Agent 和 Referer，用户 Cookie 不发给视频 CDN；上游取流时不带请求头，检测时会把用户 Cookie 发给 CDN。
- 接口状态 10011（「Request params error」附「当前服务繁忙」）按可重试处理，不判为链接无效：不存在的抖音号与服务繁忙返回完全相同，无法区分。4001038 仍判为直播间不存在。
- 接口缺少原画地址时跳过原画、继续使用其他档位，上游会报错。
- 网页主页链接直接从链接中取 `sec_uid`，省去上游的第一次请求，结果相同。
- 同一主播的直播间链接和主页链接可能得到不同的房间标识，按 `anchor_id`（`sec_uid`）去重。

**有意差异 · 快手解析**（参考 StreamGet v4.0.10 `KwaiLiveStream`）：
- 先完整解析页面状态（把 JavaScript `undefined` 换成 `null`），失败时退回上游只截取 `liveStream` 片段的做法。上游的正则截断在 `errorType` 之前，会把所有错误都报成「IP 被封」。
- 「错误代码22」和空页面无法与限流区分，按可重试处理；登录提示判为需要登录，验证码和「太频繁」判为限流，不存在、封禁、注销判为链接无效。
- 用户 Cookie 只用于用户信息接口的预检；该接口返回验证码或无法识别时退回房间页，上游会直接失败。房间页和取流都不带 Cookie。
- 录制前对选中的 FLV 做一次 HEAD 探测，连接失败时按抖音的规则换档；上游对快手不做探测。
- 缺少地址的画质档位会跳过，不影响其他档位。
- 暂不支持 `v.kuaishou.com` 等分享短链：上游只识别 `live.kuaishou.com/u/` 链接，也没有可供验证的真实短链。

**有意差异 · B站解析**（参考 StreamGet v4.0.10 `BilibiliLiveStream`）：
- 主播昵称和标题都取自 `getH5InfoByRoom`，每次检测两次请求（`room_init` 加它）；该接口没有昵称时才请求 `Master/info`。上游每次都请求这三个接口。
- 不存在的房间（`room_init` 60004、取流接口 19002003）判为链接无效，`-101` 判为需要登录，`-352`、`-412` 等风控和其他非零状态、HTTP 412 及非 JSON 响应按限流重试；锁定的直播间判为链接无效，加密且未验证的判为需要登录。上游遇到任何异常都当作未开播。
- `playUrl` 失败改用 `getRoomPlayInfo` 时取 H.264 的 FLV（没有再取其他 FLV、HLS ts）。上游按画质下标在按 `current_qn` 排序的编码列表里取，会在 H.264 和 HEVC 之间随机落点。
- 轮播（`live_status` 2）与上游一样算未开播。
- 取流请求头带 PC User-Agent 和 `Referer: https://live.bilibili.com/`，用户 Cookie 不发给视频 CDN；上游取流时不带请求头。
- 不做取流前的 HEAD 探测和换档：B站接口本身按账号权限降档，返回的就是可用的那一档。
- 暂不支持 `b23.tv` 分享短链：上游只识别 `live.bilibili.com` 链接。
- 实测 B站 FLV 时间戳只到毫秒，30 fps 的流用 FFmpeg 默认的 `-f null` 检查时会有个别「non monotonically increasing dts」提示（输出时基 1/30 秒，两帧落进同一格），并非解码错误；联网测试用 `-fps_mode passthrough -enc_time_base demux` 检查，结果 0 错误。
**有意差异 · 虎牙解析**（参考 StreamGet v4.0.10 `HuyaLiveStream`；StreamCap 调用 `fetch_app_stream_data`）：
- 支持画质档位。上游的接口路径（非英雄联盟直播间）不看画质，总是录原画；录播宝按接口的 `bitRateInfo` 建档：原画（`iBitRate` 为 0，不带 `ratio`）在前，其余按码率从高到低，在流地址后加 `&ratio={码率}`，按位置对应原画、超清、高清、标清、流畅，缺档用最后一档补齐。英雄联盟直播间的网页路径同样按 `vMultiStreamInfo` 建档；上游按防盗链参数里的 `exsphd` 取码率，现在的页面已没有这个字段，上游在这条路径上也只能录原画。
- 只保留 H.264 档位：赛事直播间会列出 `2K HDR` 等 H.265 档（`iCodecType` 为 1，流名不同），上游生成的防盗链参数固定 `codec=264`，拿不到这些档。
- 录制前对选中的 FLV 做一次 HEAD 探测，连接失败时按抖音的规则换档；上游不做探测。
- 只识别 `www.huya.com`、`huya.com`、`m.huya.com` 下单段路径的直播间链接；上游按 `*.huya.com` 注册、取最后一段路径，会把 `v.huya.com` 视频页等也当成直播间。
- 字母标识的页面找不到房间号时，页面写着「找不到此页面」判为链接无效，空页面或验证页判为限流，其余判为解析失败并提示改用房间号；上游一律报错。接口返回 422（「该主播不存在！」）判为链接无效。
- 虎牙部分页面（如赛事直播间）不管请求头都返回 gzip 压缩内容，录播宝的 HTTP 客户端未开解压，按 gzip 魔数自行解压。
- 防盗链参数的 MD5 和 base64 在 `huya.rs` 内手写实现，免得为一个算法新增依赖（与抖音的 SM3 相同做法）。
- 用户 Cookie 只发给虎牙的接口和页面，不发给视频 CDN；上游取流时不带请求头。
- 低码率转码档（如 `ratio=500`）的源流本身就有少量重复的音频时间戳（直接下载源 FLV 也能复现），FFmpeg 检查时会报 `non monotonically increasing dts`，画面和声音都能完整解码；原画没有这个现象。
**有意差异 · 斗鱼解析**（参考 StreamGet v4.0.10 `DouyuLiveStream`）：
- 只接受 `www.douyu.com`、`douyu.com` 和 `m.douyu.com`；上游按 `https://.*\.douyu\.com/` 注册，`v.douyu.com` 视频页等也会进到斗鱼解析。专题页（`/topic/…`）必须带 `rid`，不带时在添加时说明原因；上游会去请求 `m.douyu.com/topic` 然后报错。
- 不存在或已关闭的房间，`betard` 返回「提示信息」网页而不是 JSON，判为链接无效并带上斗鱼的提示（「该房间目前没有开放」「您观看的房间已被关闭…」）；上游在解析 JSON 时出错。
- 取流接口返回 -5「房间未开播」时按未开播处理，-3「房间不存在」判为链接无效，其他错误带上错误码和提示（提到登录的判为需要登录，其余按可重试处理）；上游遇到错误时不报原因，结果是「在播但没有地址」。
- 只取斗鱼默认线路的一条 FLV，不再为其他 CDN 线路逐条签名请求；上游把它们放进 `backup_url_list`，StreamCap 并不使用。
- 画质列表来自取流接口的 `multirates`，只有斗鱼实际返回的那一档带地址。斗鱼会把房间没有的档位换成相近的一档：实测 24422 请求原画（rate 0）返回「蓝光4M」（rate 4），请求流畅（rate 1）返回「高清」；上游发的是同样的请求，结果相同。
- 签名用到的 MD5 在 `douyu.rs` 里自带实现（有标准测试向量），没有新增依赖，也不需要 JavaScript 引擎。
- 用户 Cookie（可选）和上游一样随房间页和接口请求发送，不发给视频 CDN。

**有意差异 · 小红书解析**（参考 StreamGet v4.0.10 `RedNoteLiveStream`，StreamCap `RedNoteHandler`）：
- 只接受 `www.xiaohongshu.com/livestream/…/{房间号}`（可带 `dynpath…` 段和 `host_id` 等参数）和 `xhslink.com/…` 分享短链；上游按 `www\.xiaohongshu\.com/` 注册，任何小红书页面都会进到解析。小红书的直播间按场次编号，链接只在那一场有效，下播后一直判为未开播（上游 README：一次性地址，暂不支持循环监控），录播宝沿用这一行为。
- 主页链接（`/user/profile/{id}`）能识别，但添加时说明主页无法判断是否开播、请改用直播间链接；上游接受主页链接，只读到昵称，任务永远不会开播。
- 分享短链跳转后不是直播间（失效的短链跳到首页，例如 README 示例 `xhslink.com/xpJpfM`）判为链接无效并说明「已失效」；上游拿首页继续解析，结果是未开播且昵称为空。
- 页面 `pageStatus` 为 `error`（「未找到直播间，请稍后再试」）判为链接无效并带上小红书的提示；空页面或没有页面数据判为限流（可能是验证页）；上游一律按未开播处理。
- 开播判断与上游相同（`liveStatus` 为 `success` 且标题不含「回放」），但标题为空时也算开播；上游要求有标题。昵称取页面的 `hostInfo.nickName`（下播后页面也有），不再去请求主页；主播 id 取 deeplink 或链接里的 `host_id`。只读当前直播间的数据，不读页面里推荐的下一个直播间（`nextRoomInfo`）。
- `__INITIAL_STATE__` 里的 `undefined` 只替换字符串以外的，免得改坏标题；上游全文替换。
- 流地址与上游相同：从 deeplink 的 `flvUrl` 取流名，拼 `http://live-source-play.xhscdn.com/live/{流名}.flv` 和同名 `.m3u8`，录 FLV。小红书只有一档（页面的 `pullConfig` 里也只有「原画」），所有画质都录这一条。取不到 `flvUrl` 时用房间号作流名（上游会出错）。

- 接受 `live.baidu.com` 下带 `room_id={纯数字}` 查询参数的链接，归一为 `https://live.baidu.com/m/media/pclive/pchome/live.html?room_id={房间号}`；上游用正则 `room_id=(.*?)&` 取房间号，`room_id` 在最后一个参数时（没有后续 `&`）会失败，这里按查询参数解析，两种写法都认。
- 房间不存在时接口返回 `data.371` 为空，判为链接无效；上游在读主播名时出错。`status` 为 `"0"` 才算开播，回放（实测 `"20"`）判为未开播，与上游一致。
- 画质与上游一致：`url_clarity_list` 非空时取其 `urls.flv` 的文件名，否则取 `url_list[].urls[0].hls` 的文件名，拼到 `https://hls.liveshow.bdstatic.com/live/` 得到 m3u8，只录 HLS；按接口给的顺序（实测 720p、480p）建档，依次对应原画、超清，其余补最后一档。
- 请求使用上游固定的 H5 设备号（上游在三个里随机选一个，这里固定用第一个）和 `ua=360_740_ANDROID_0`；不需要登录，用户 Cookie（可选）只发给接口，取流不带。主播昵称为空时用「百度直播 {房间号}」。

**有意差异 · 知乎 解析**（参考 StreamGet v4.0.10 `ZhihuLiveStream`，StreamCap `ZhihuHandler`，平台键 `zhihu`；`display_name` 为「知乎直播」，界面短名「知乎」）：
- 只接受 `zhihu.com/theater/{纯数字}`（也认 `www.zhihu.com`），归一为 `https://www.zhihu.com/theater/{直播间号}`；`drama_id` 每场直播不同，不进归一后的链接，同一直播间的不同链接按直播间号去重。上游按 `zhihu.com/` 注册，只要求链接里有 `/theater/` 并取最后一段当直播间号。

**有意差异 · 猫耳FM 解析**（参考 StreamGet v4.0.10 `MaoerLiveStream`，StreamCap `MaoerFMHandler`，平台键 `maoerfm`；`display_name` 为「猫耳FM直播」，界面短名「猫耳FM」）：
- 只接受 `fm.missevan.com/live/{纯数字}`（可带查询参数），归一为 `https://fm.missevan.com/live/{房间号}`；上游按 `fm.missevan.com/` 注册，取路径最后一段当房间号，其他页面也会进到解析再出错。

**有意差异 · 桌面行为**（参考 StreamCap `app/lifecycle/`、`app/messages/desktop_notify.py`）：
- 系统通知：与上游一样，总开关 `system_notification_enabled` 控制全部系统通知，开播通知只在主窗口隐藏或最小化时发。不同的是，上游的「开播通知」「下播通知」开关只管推送渠道，0.1.0 没有推送渠道，这两个开关改为控制系统通知：开播默认开、下播默认关。「仅通知」的直播间开播时只看总开关，不受「开播通知」开关和窗口状态影响（否则关掉开播通知后这类直播间既不录也不提醒）。任务进入「需处理」时提醒一次（上游没有）。短时间内的多条开播或下播合并成一条。
- 关闭窗口：与上游一样询问「最小化到托盘 / 退出 / 取消」，另加「记住我的选择」，存入设置 `close_window_action`（`ask`、`tray`、`quit`），可在设置页「托盘与通知」修改。托盘创建失败（例如 Linux 没有 AppIndicator 库，启动时先探测）时关窗直接退出。GNOME 没装 AppIndicator 扩展时库存在但托盘不显示，隐藏后可以再次启动录播宝唤回窗口（单实例）。Linux 托盘不支持提示文字，改用标题：有录制时显示「录播宝 · 录制中 N」，平时显示「录播宝」。
- 托盘菜单：上游只有「恢复」「退出」；录播宝另有「全部暂停监控」「全部恢复监控」。有录制时全部暂停先确认；全部恢复只恢复本次运行中由「全部暂停」暂停的直播间，用户单独暂停的保持暂停。
- 退出：上游按录制数固定等待几秒后强制退出；录播宝停止每个录制并等文件收尾（最多 30 秒）。系统直接结束进程时（macOS Dock「退出」、Windows 注销或关机）无法确认，限时 4 秒同步收尾；Linux 注销或关机时进程收到 SIGTERM，按普通退出收尾（不再确认）。
